## 2026-08-25

- [2026-08-25-package-namespaces-and-typeformatter-analysis.md](2026-08-25-package-namespaces-and-typeformatter-analysis.md) — Implemented Stages A1 and B of the previous session's design. **A1**: `PackageGraph.name` deleted, `PackageKind`/`PackageManifestKind` now fieldless — a package has no name of its own, it's known by the key a dependent declared it under, so the name lives on the `(declaring package, key)` edge as `dependencies: HashMap<SymbolU32, PackageId>` plus its inverse `dependency_names`, well-defined only because `add_dependency` keeps the mapping injective and reports its own diagnostics (new `E2004` `StdPackageAsDependency`, `E2005` `PackageDeclaredTwice`); the manifest key is settled as a *declaration*, not an alias, which keeps a future `use x as y` orthogonal instead of conflicting; `package_by_name` deleted in favour of a non-optional `stdlib_package: PackageId`. **B**: every package — root included — now owns a root namespace, which un-overloads `None` (it had meant both "the root package's own top-level scope" and "no parent") and fixes three bugs at once, confirmed empirically beforehand via a root package calling `shared::from_shared()` with zero diagnostics despite never declaring `shared`: transitive dependencies nameable from anywhere, `std` able to see the root's private items, and `module std;` silently merging into the stdlib's namespace. Net-subtractive — `TIR.root_symbols`/`root_wildcard_imports`, `lookup_global_symbol`'s global fallback, `ModuleNamespace.name`, the `PackageId` in `ModuleDeclarationKind::Package`, and the `is_ancestor_or_self` crate-root guard (a workaround for exactly this conflation, documented as a pitfall in CLAUDE.md) are all gone; replaced by `package_namespaces` + `file_namespaces` (a `Vec` indexed by `FileId`) and a `package: PackageId` on every namespace. Dependency edges are materialized as ordinary `Module` symbols in the declaring package's own namespace — a dependency *is* an implicit `module <key>;` at the top of the entry file — so nothing global is involved and a package's dependencies stay invisible to its own dependents. Naming a namespace became contextual and total (`namespace_name(ns, packages, from) -> SymbolU32`) rather than `Option`, since dropping names from diagnostics is worse than threading context; storing the name on `Type::Namespace` was rejected (a name is not a property of a type). `Option<NamespaceIndex>` removed codebase-wide (~40 signatures). **`TypeFormatter` analysis**: `type_params` was **dead** — written by `with_type_params`, never read, since the `Type::TypeParam` arm resolves names entirely from `owner` + `tir`; removed with its three no-op LSP call sites. The planned "collapse `interner`/`id_generator`/`files`/`packages` into one `&mut CompilationUnit`" was **proven impossible** and its TODO (which had claimed feasibility by checking the wrong lifetime) corrected in place: `ast_nodes` holds `&'ast ast::Item` pointing *into* the same `CompilationUnit`, legal only because `packages` and `interner` are disjoint fields — behind one `&mut` the AST refs must reborrow out of it, poisoning the builder for every later `&mut self` phase (E0502, reproduced standalone). Consequence: the formatter needs shared `interner` + shared `packages` while the builder holds mutable `interner`, so no single owner exists to name; the achievable form is a *narrower* `NameContext { interner, packages, from }`, deferred. Also found: `packages`/`from` serve exactly one match arm (`Type::Namespace`) for all 89 call sites; `display_type`/`display_bounds` should be infallible (30 `.unwrap()`s, 6 `.unwrap_or_default()`s that render an empty type name into hover text); `pub interner` exists only for four sites, two of them `.unwrap_or("?")`

- [2026-08-23-format-cli-and-stdlib-provider-design.md](2026-08-23-format-cli-and-stdlib-provider-design.md) — Design-only, resolving the previous session's Open question 1. **`wx format`**: none of the three shapes (A/B/C) from that devlog was picked; the problem was re-decomposed into two orthogonal axes after noticing `load_package` already walks the module tree from an entry file with no manifest involved — so "format a package" and "format a module tree without a manifest" are the *same call*, and the manifest is purely a config source. Implicit std becomes a merged default (`dependencies.entry("std").or_insert(Builtin)` on the root only), deleting `resolve.rs:94-97`'s `package_by_name` probe and collapsing default/override into one path; opting out is a third fieldless package type `{"type": "std"}` (chosen over a `DependencySource::None` variant, a `no_std` boolean whose 2×2 has an undefined cell, a CLI flag, opt-in std, and deriving it from tag definitions — all recorded with reasons). `CompilationUnit.stdlib_package` is a non-optional `PackageId` enforced via `build(root_package, stdlib_package)`; all 12 call sites already call `load_stdlib()` and discard the id it returns. Two things this surfaces: `#[tag = "..."]` is completely ungated today (`builder.rs:4378-4384`, bare `tagged_items.insert`, last-wins across packages — any user package can silently hijack `+`), and `resolve_operator_trait`'s `panic!`s become reachable from a two-line `wx.json` the moment any user-facing opt-out exists, so panic→diagnostic is a prerequisite. - [2026-08-17-chained-inlining-offset-collision-investigation.md](2026-08-17-chained-inlining-offset-collision-investigation.md) — Deep dive on the chained-inlining bug above: exact mechanism (`LocalSet` writes directly into a shared, mutating vector, unlike `Block`'s own clone-extend-discard, which is what makes `if`/`else`/`Aggregate`/etc. safe). Two fix candidates worked out: (1) stop `compute_locals_offsets` from sharing offsets between siblings at all — trivial, provably safe, zero cost since the vector it feeds is discarded before codegen, but felt like patching around the real problem rather than fixing it; (2) make `inline_call`'s own scope tree honestly reflect non-exclusive nesting. Within (2), a first attempt (thread scope through `Call`'s own arguments) is proven *insufficient* via a hand-traced counterexample (`test_lerp`'s `a + (b-a)*t` — three separate inlining sweeps, one per operator method, where an already-substituted `Block` from an earlier sweep still collides); a second attempt (chain onto whichever of the true call site or the globally-last-created scope has the larger occupied range) is hand-verified correct against both known failure shapes and needs no explicit threading at all. Neither implemented that day — user asked to stop and just record findings; everything reverted, back to pre-investigation baseline (715/2). Superseded by an even simpler fix, see below
- [2026-08-17-chained-inlining-offset-collision-fix.md](2026-08-17-chained-inlining-offset-collision-fix.md) — Fixed, later the same day, with a *different, simpler* design than either candidate above: instead of protecting a new per-call scope from colliding with a sibling's, stopped creating that scope at all — `inline_call` now appends the callee's own root-scope locals (its parameters, and any `local` it declares directly) onto the caller's *existing* scope at the call site, so a second inlined call there just gets index ranges past the first's, nothing to compare or protect (`Vec::push` can't collide with itself). The break-target wrapper scope still exists unconditionally but never holds locals, so it's always safe to parent at the call site directly. Generalized the pre-existing `Rebaser` (used elsewhere for combining globals' initializers into the start function) to cover both the new root-redirect case and the old plain-shift case, removing a duplicate tree-walk. One accepted regression: `opt::tests::test_simple_add` now produces one extra dead SSA node per inlined call at a function's root (root-scope default-seeding fires for locals inlining adds past the declared params) — harmless (reused via CSE, doesn't affect WASM output), test updated rather than fixed. Also checked and ruled out (with a new empirical regression test, not just on paper) whether `MIR::build_start_function`'s globals-combining shares the same bug shape — it doesn't, because each global's init is always a self-contained `Block` value routed through the same clone-then-discard mechanism that makes `if`/`else` safe. 732 passed / 0 failed

## 2026-08-17

- [2026-08-17-compound-assignment-trait-dispatch-design.md](2026-08-17-compound-assignment-trait-dispatch-design.md) — Design-only: `+=`/etc. as sugar over resolved `Add`-style trait dispatch. Records the rejected shapes and why (full TIR-level `place = place.add(rhs)` desugar blocked by `Expression`/`Place` not being `Clone`, plus a confirmed pre-existing double-evaluation bug in `lower_compound_assignment`'s `Load{place}` handling independent of trait dispatch; a single `CompoundAssign` node with `Option<DefId>` conflated "typeset-bounded" with "genuinely unsupported"; a target-kind split into `LocalSet`/`GlobalSet`/`FieldSet` left `FieldSet` depending on an invariant enforced elsewhere). Key insight: typeset-bounded (`Mem::Size`) and generic-not-yet-concrete (`T: Add`) are the same category — both resolve via monomorphization's existing substitution machinery, confirmed against how `GenericMethodCall` already resolves abstract trait methods at MIR-lowering time via `find_trait_impl`. Final design: new TIR-only `BinaryOp` excluding assignment operators, a new `Assign` node for plain `=`, and four compound-assignment nodes split two ways (resolved-now vs. deferred-to-monomorphization × plain-`Expression`-target vs. `Place`-target) — `CompoundAssign`/`GenericCompoundAssign`/`CompoundStore`/`GenericCompoundStore`
- [2026-08-17-compound-assignment-implementation-and-deferred-bugs.md](2026-08-17-compound-assignment-implementation-and-deferred-bugs.md) — Implemented the design above end to end (609/104 → 711/2 passing). Along the way: fixed `report_unused_items` firing on trait impl methods (reused the already-free `TypeParamOwner::TraitImpl(_)` signal, matching Rust); fixed `opt::tests::TestCase::get_first_func`'s stale "no stdlib" assumption via tag-based lookup, which led to the real bug — `extend_bindings`/`extend_bindings_in_place` unconditionally seeding default-value nodes for inlined-call scopes whose locals were already populated via `LocalSet`, fixed and independently adversarial-reviewed. That review surfaced two items, both since resolved: a chained-inlining flat-offset collision that silently clobbers a staged value with a sibling's (confirmed value-correctness bug via wasmtime, same root cause as `test_lerp`'s trap — fixed later the same day, see [2026-08-17-chained-inlining-offset-collision-fix.md](2026-08-17-chained-inlining-offset-collision-fix.md)), and `char` missing `impl Sub`/`impl Add` — resolved, not a gap: deliberately no impl at all, since unconstrained arithmetic could produce a `char` bit pattern outside the valid Unicode-scalar-value range with no checkpoint to reject it; arithmetic requires an explicit cast to an integer type and back, matching `std/main.wx`'s own `to_ascii_uppercase`/`to_ascii_lowercase` idiom
- [2026-08-17-chained-inlining-offset-collision-investigation.md](2026-08-17-chained-inlining-offset-collision-investigation.md) — Deep dive on the chained-inlining bug above: exact mechanism (`LocalSet` writes directly into a shared, mutating vector, unlike `Block`'s own clone-extend-discard, which is what makes `if`/`else`/`Aggregate`/etc. safe). Two fix candidates worked out: (1) stop `compute_locals_offsets` from sharing offsets between siblings at all — trivial, provably safe, zero cost since the vector it feeds is discarded before codegen, but felt like patching around the real problem rather than fixing it; (2) make `inline_call`'s own scope tree honestly reflect non-exclusive nesting. Within (2), a first attempt (thread scope through `Call`'s own arguments) is proven *insufficient* via a hand-traced counterexample (`test_lerp`'s `a + (b-a)*t` — three separate inlining sweeps, one per operator method, where an already-substituted `Block` from an earlier sweep still collides); a second attempt (chain onto whichever of the true call site or the globally-last-created scope has the larger occupied range) is hand-verified correct against both known failure shapes and needs no explicit threading at all. Neither implemented that day — user asked to stop and just record findings; everything reverted, back to pre-investigation baseline (715/2). Superseded by an even simpler fix, see below
- [2026-08-17-chained-inlining-offset-collision-fix.md](2026-08-17-chained-inlining-offset-collision-fix.md) — Fixed, later the same day, with a *different, simpler* design than either candidate above: instead of protecting a new per-call scope from colliding with a sibling's, stopped creating that scope at all — `inline_call` now appends the callee's own root-scope locals (its parameters, and any `local` it declares directly) onto the caller's *existing* scope at the call site, so a second inlined call there just gets index ranges past the first's, nothing to compare or protect (`Vec::push` can't collide with itself). The break-target wrapper scope still exists unconditionally but never holds locals, so it's always safe to parent at the call site directly. Generalized the pre-existing `Rebaser` (used elsewhere for combining globals' initializers into the start function) to cover both the new root-redirect case and the old plain-shift case, removing a duplicate tree-walk. One accepted regression: `opt::tests::test_simple_add` now produces one extra dead SSA node per inlined call at a function's root (root-scope default-seeding fires for locals inlining adds past the declared params) — harmless (reused via CSE, doesn't affect WASM output), test updated rather than fixed. Also checked and ruled out (with a new empirical regression test, not just on paper) whether `MIR::build_start_function`'s globals-combining shares the same bug shape — it doesn't, because each global's init is always a self-contained `Block` value routed through the same clone-then-discard mechanism that makes `if`/`else` safe. 732 passed / 0 failed

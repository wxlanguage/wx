- [2026-08-25-module-collision-diagnostics-and-phase1-redesign.md](2026-08-25-module-collision-diagnostics-and-phase1-redesign.md) — Follow-up to the same day's namespace refactor, closing its first follow-up item (`ensure_module`'s duplicate rule). Three name-owning mechanisms — a `wx.json` dependency, an `import { }` block, and a user `module` — could each silently steal another's binding with zero diagnostic; worst case, a file-declared `module std;` didn't just merge but *replaced* the real `std` binding outright, so `use std::*;` silently resolved against the user's own file and surfaced as a cascade of unrelated "undeclared type" errors with nothing pointing at the cause. All three now report `E1000` (`DuplicateDefinition`). Fixing it properly (not just adding a kind-check) meant splitting `TIR::build`'s Phase 1 into two passes: 1a creates every file's namespace directly from vfs's `SourceModule.declaration` — safe because `ModuleId`s are assigned in push order, so a parent's is always numerically less than its children's — with every `ModuleDecl` field set exactly once at construction; 1b (`pre_scan_item`) is now a pure reader of `file_namespaces`, and its `ModuleDeclaration` arm (previously a call whose return value was discarded, existing solely for a `pub_span` side effect) is a no-op. This eliminated a pre-existing `if decl.pub_span.is_none() { decl.pub_span = pub_span }` mutation entirely, by removing the two-callers-racing situation it was defending against rather than just guarding it. Along the way, vfs's `SourceModule` gained a proper `ModuleDeclaration { parent, name, pub_span }` bundling what were three independently-optional fields that always existed or didn't *together*. New shared `check_module_collision` helper (direct-scope only, not the ancestor-walking `lookup_global_symbol`) is used by `ensure_module` (now down to one caller: inline `module foo { }` blocks), Phase 1a itself, and `pre_scan_item`'s pre-existing, unrelated `Import` arm (which had the identical unconditional-`insert_symbol` bug — fixed with the added nuance that the missing-alias fallback identifier, an unescaped import-path string like `"wasi_snapshot_preview1"`, is never a real user-chosen name and so is excluded from both the check and the binding entirely, not just the check). Separately: vfs's child-declaration scan was flat, so `module extra;` nested inside an inline `module utils { }` block was invisible rather than diagnosed — fixed as detection-only (new `E2006`), deliberately not resolution: Rust supports this (accumulating a directory segment per inline nesting level) but it was rejected as adding a real conflict with the Phase 1a/1b split (a nested file declaration's parent *namespace* wouldn't exist until Phase 1b creates it) on top of the readability cost of not being able to tell where a `module foo;` file lives without walking up through its enclosing inline wrappers. **Also fixed**: a module's children used to resolve relative to its own file's *physical* directory (`self.modules[parent_module_id].file_path.parent()`) rather than a directory named after the module itself, so a plain-sibling file like `a.wx` (living directly in `src/`, not `src/a/mod.wx`) never actually nested `shared` under `a` when it declared `module shared;` — it landed in `src/shared.wx`, a plain sibling of `main.wx` itself, indistinguishable from (and colliding with) any other sibling file declaring the same name. Rust's own diagnostic (`E0583`, suggesting `.../a/shared.rs`) confirms it always grants a module its own directory per path segment regardless of file form; fixed by threading an accumulated `owned_dir: AbsolutePath` through `Loader::load_module`/`resolve_child_module_path` (`<parent's owned_dir>/<child's name>`, computed the same way regardless of which form resolved the child's own file) instead of deriving it from the file path, making `math.wx` and `math/mod.wx` fully interchangeable for what directory `math`'s children live in — and making the collision impossible by construction rather than needing a new restriction or diagnostic (an unresolvable path is just an ordinary `ModuleFileNotFound`). 828 `wx-compiler` + 53 `wx-lsp` passing (six new regression tests, no regressions)
- [2026-08-25-package-namespaces-and-typeformatter-analysis.md](2026-08-25-package-namespaces-and-typeformatter-analysis.md) — Implemented Stages A1 and B of the previous session's design. **A1**: `PackageGraph.name` deleted, `PackageKind`/`PackageManifestKind` now fieldless — a package has no name of its own, it's known by the key a dependent declared it under, so the name lives on the `(declaring package, key)` edge as `dependencies: HashMap<SymbolU32, PackageId>` plus its inverse `dependency_names`, well-defined only because `add_dependency` keeps the mapping injective and reports its own diagnostics (new `E2004` `StdPackageAsDependency`, `E2005` `PackageDeclaredTwice`); the manifest key is settled as a *declaration*, not an alias, which keeps a future `use x as y` orthogonal instead of conflicting; `package_by_name` deleted in favour of a non-optional `stdlib_package: PackageId`. **B**: every package — root included — now owns a root namespace, which un-overloads `None` (it had meant both "the root package's own top-level scope" and "no parent") and fixes three bugs at once, confirmed empirically beforehand via a root package calling `shared::from_shared()` with zero diagnostics despite never declaring `shared`: transitive dependencies nameable from anywhere, `std` able to see the root's private items, and `module std;` silently merging into the stdlib's namespace. Net-subtractive — `TIR.root_symbols`/`root_wildcard_imports`, `lookup_global_symbol`'s global fallback, `ModuleNamespace.name`, the `PackageId` in `ModuleDeclarationKind::Package`, and the `is_ancestor_or_self` crate-root guard (a workaround for exactly this conflation, documented as a pitfall in CLAUDE.md) are all gone; replaced by `package_namespaces` + `file_namespaces` (a `Vec` indexed by `FileId`) and a `package: PackageId` on every namespace. Dependency edges are materialized as ordinary `Module` symbols in the declaring package's own namespace — a dependency *is* an implicit `module <key>;` at the top of the entry file — so nothing global is involved and a package's dependencies stay invisible to its own dependents. Naming a namespace became contextual and total (`namespace_name(ns, packages, from) -> SymbolU32`) rather than `Option`, since dropping names from diagnostics is worse than threading context; storing the name on `Type::Namespace` was rejected (a name is not a property of a type). `Option<NamespaceIndex>` removed codebase-wide (~40 signatures). **`TypeFormatter` analysis**: `type_params` was **dead** — written by `with_type_params`, never read, since the `Type::TypeParam` arm resolves names entirely from `owner` + `tir`; removed with its three no-op LSP call sites. The planned "collapse `interner`/`id_generator`/`files`/`packages` into one `&mut CompilationUnit`" was **proven impossible** and its TODO (which had claimed feasibility by checking the wrong lifetime) corrected in place: `ast_nodes` holds `&'ast ast::Item` pointing *into* the same `CompilationUnit`, legal only because `packages` and `interner` are disjoint fields — behind one `&mut` the AST refs must reborrow out of it, poisoning the builder for every later `&mut self` phase (E0502, reproduced standalone). Consequence: the formatter needs shared `interner` + shared `packages` while the builder holds mutable `interner`, so no single owner exists to name; the achievable form is a *narrower* `NameContext { interner, packages, from }`, deferred. Also found: `packages`/`from` serve exactly one match arm (`Type::Namespace`) for all 89 call sites; `display_type`/`display_bounds` should be infallible (30 `.unwrap()`s, 6 `.unwrap_or_default()`s that render an empty type name into hover text); `pub interner` exists only for four sites, two of them `.unwrap_or("?")`

# 2026-08-16 — Primitives as intrinsic type-alias items; `use` wildcard-import scoping bug found

## Summary

Turned primitive types (`i8`..`f64`, `bool`, `char`, `never`) from a hardcoded string match in the type resolver into real `#[intrinsic] pub type X;` items declared in `std/main.wx`, giving them a `DefId` and making LSP go-to-definition/hover/find-references work on them. Fixing the resulting hover regression (bodiless aliases rendering as `pub type u8 = u8`) led to auditing whether primitives should be visible without an explicit `use std::*;`, which surfaced a pre-existing bug: a root-level `use X::*;` in wx is currently crate-wide, not per-file, unlike Rust. Implementing that fix properly was scoped out as its own task; today's change stays scoped to the 3 wx-lsp tests that needed an explicit `use std::*;` added.

## Changes

### Primitives as `#[intrinsic] type` items

- `ast/mod.rs`: `Item::TypeAlias.ty: Box<Spanned<TypeExpression>>` → `body: Option<Box<Spanned<TypeExpression>>>`. `parse_type_alias_item` now accepts a bodiless `type Name;` form (no `= TypeExpr`).
- `tir/mod.rs`: `TypeAlias` gained an `attributes: Box<[ItemAttribute]>` field. New `MissingTypeAliasBody` (`E1070`) diagnostic, worded like rustc's "free type alias without body" message (with a `help:` secondary label).
- `tir/builder.rs`: `ensure_signature`'s `TypeAlias` arm branches on body presence — with a body, resolves normally; without one, binds to the matching primitive `TypeIndex` if `#[intrinsic]` is set (trusting the origin, same policy as intrinsic functions — no validation that the name is a real primitive or that intrinsic+body aren't combined, since only the stdlib we control uses the attribute today), else reports `MissingTypeAliasBody`. Deleted the old unconditional `Type::try_from(&str)` shortcut in `resolve_type_identifier` — this was the actual source-of-truth removal that made real items matter.
- `std/main.wx`: added `#[intrinsic] pub type X;` for all 13 names the old shortcut handled (`i8, u8, i16, u16, i32, u32, i64, u64, f32, f64, bool, char, never` — not just the 10 numeric ones originally proposed; `bool`/`char`/`never` would have silently become unresolvable otherwise).
- `wx-fmt/src/lib.rs`: `build_type_alias_definition` now prints attributes and omits `= <type>` when there's no body.

### Hover fix + `TypeAlias::body` doc comment

`wx-lsp`'s hover for a type alias unconditionally appended `" = " + display_type(alias.body)`. Since `body: TypeIndex` (not `Option`) is always populated post-resolution — even for bodiless intrinsics, where it just holds the resolved primitive — this rendered `#[intrinsic] pub type u8;` as `pub type u8 = u8`. Fixed by checking `alias.attributes.contains(&ItemAttribute::Intrinsic)` before appending the `= Type` part. Considered adding a separate `has_body: bool` field instead of overloading the `Intrinsic` check, but landed on keeping `body: TypeIndex` non-optional (real consumers — name resolution, `substitute_type` during monomorphization — never see it absent) and documenting *why* directly on the field rather than adding new state.

### Unrelated `wx-fmt` bug found and fixed

`build_impl_item`'s `ast::ImplItem::Constant` arm never read `pub_span`/`attributes` at all — every `impl Foo { pub const X = ...; }` silently lost its `pub` (and any attribute) on format. This had already round-tripped through the real `std/main.wx` (the `impl f32 { pub const PI }` / `impl f64 { pub const PI }` blocks lost their `pub`), which broke ~100 compiler tests (`case.tir.diagnostics.is_empty()`) with a spurious "const `PI` is never used" warning once `PI` was no longer reachable from anywhere. Fixed the formatter and restored `pub` on both `PI` consts.

## Key findings

- **`std/main.wx` items are not implicitly visible anywhere — `use std::*;` is required, and every compiler test auto-prefixes it.** `TestCase::new`/`new_multi_file` in `tir/tests.rs` silently prepend `"use std::*;\n"` to the entry source. This is why removing the primitive shortcut broke plain `wx-cli check` on a file as simple as `fn test() -> u32 { 0 }` (`error[E1021]: undeclared type`) despite the compiler's own test suite staying green — the tests were never actually exercising the "no import" path primitives used to get for free via the old shortcut.

- **A root-level `use X::*;` in wx is crate-wide, not per-file — confirmed empirically, not just by reading the code.** Wrote a throwaway `TestCase::new_multi_file` probe: entry file has `use std::*;` at its root; a completely separate `module child;` file (`src/child.wx`) writes *no* `use` at all and bare-references `u32`. It resolved with zero diagnostics. Root cause: `use X::*;` written at `namespace: None` (the crate-root scope) is recorded into `Builder::root_wildcard_imports: Vec<NamespaceIndex>` — a single flat list — and `lookup_global_symbol` consults that list unconditionally for *every* lookup, once its own ancestor chain is exhausted, regardless of which file/namespace the lookup started in. There is no per-file scoping at all for a root-level `use`.

- **The same bug isn't limited to the crate-root case — it's structural.** `lookup_global_symbol`'s single ancestor-walk loop checks each namespace's own `wildcard_imports` *while walking up to parents* — the same walk that implements privacy's "visible to declaring namespace and every descendant namespace." So `use Foo::*;` written inside `module A { use Foo::*; module B { ... } }` already leaks into `B` too, today, independent of anything from this session. Privacy-ancestry and import-lookup are two different concerns (Rust: privacy is visible-to-descendants, `use` is never inherited by any descendant) that share one mechanism in wx's current implementation.

- **Duplicate inherent-impl members are only caught at first use, not at the second declaration — and not at all if the duplicate is never referenced.** `impl f32 { const PI = ...; }` twice (once in `std/main.wx`, once in user code) produces no diagnostic until something actually references `f32::PI`, at which point `resolve_inherent_member` reports it as an "ambiguous"-shaped `E1000` at the *use* site rather than at the second `impl` block. Root cause: `inherent_impl_dispatch` is keyed by `(ImplTarget, member_name)`, and `ImplTarget` is coarser than a full concrete type (no type args) — so the same bucket can legitimately hold multiple *non-conflicting* blocks for a generic target (`impl Box<i32> { fn get }` and `impl Box<bool> { fn get }` both providing `get`, per the existing "within-block duplicate check" comment at `builder.rs:5333`). Telling a real conflict apart from that requires unifying against a concrete type, which isn't available yet for a generic block at registration time — so the check was deferred wholesale to `resolve_inherent_member`, generic and non-generic blocks alike. For a *non-generic* target like `f32` there's no such ambiguity (only one possible instantiation), so this is fixable without full overlap/coherence checking — analogous to `register_trait_impl` (`builder.rs:14520`), which already reports duplicate **trait** impls eagerly, though it can do that unconditionally because trait impls use a stricter one-per-type-constructor policy that inherent impls deliberately don't. Not fixed today — noted as its own task, same treatment as the `use`-scoping issue above.

## Decisions

- **Did not implement "std auto-imported everywhere" today.** The natural implementation (push `std`'s crate namespace into `root_wildcard_imports` unconditionally at graph-build time in `tir::builder::build`) would work and would cover multi-file projects correctly (nested `module foo::bar;` namespaces chain their `parent` back to `None` via `ensure_module_path`, so the fallback still fires no matter the nesting depth) — but it would be built on top of the crate-wide `use` bug above rather than correct per-file semantics.
- **Did not fix the `use` per-file scoping bug today either.** Doing it properly means splitting `lookup_global_symbol`'s combined ancestor-walk into two separate mechanisms — one for privacy-ancestry (keep as-is), one for import-lookup (should check only the exact namespace a reference occurs in, no walking up to parents). That's a change to the core resolution path shared by every type *and* value lookup in the compiler, and no existing test (single-file or multi-file) currently pins down the "correct" nested-module `use` behavior either way — real regression surface with no safety net. Scoped out as its own task.
- **Fixed the 3 wx-lsp tests that broke** (`hover_after_did_change_observes_latest_edit_through_backend`, `type_alias_used_as_return_type_resolves_to_its_definition`, `full_diagnostic_renders_and_handles_bad_index`) by adding `use std::*;` to their sources instead, matching what `TestCase` already does. Checked first whether this was a large blast radius (7 of ~38 `.wx` source strings in `wx-lsp/src/tests.rs` already had `use std`) — only 3 tests actually asserted on something resolution-sensitive enough to fail.

## Open questions

- Should duplicate inherent-impl members for a *non-generic* target (primitives, non-generic structs) be reported eagerly at the second declaration, reusing `unify_inherent_impl_target` the same way `resolve_inherent_member` already does at use-time but probed against the new block's own concrete type instead of a use site's? That fix wouldn't touch the deliberately-deferred generic case (`impl Box<i32>`/`impl Box<bool>` both providing `get`), which would still need real overlap/coherence checking to catch eagerly, if that's ever wanted.
- Should wx's `use` be strictly per-file/per-module (Rust-like — never inherited by any descendant, nested or crate-root), or is crate-wide-from-the-root actually intended? No test currently pins this down either way. Worth deciding explicitly before building anything else (like std-by-default) on top of `root_wildcard_imports`.
- Once `use` scoping is decided/fixed, revisit "std implicitly imported everywhere" — the mechanical piece (push std's namespace into whatever the corrected global-fallback list becomes) is small; it was only blocked on the semantics underneath being right first.
- `examples/*.wx` are stale — `examples/bump_allocator/bump_allocator.wx` doesn't even parse (`@size_of`/`@align_of` sigil syntax that no longer exists). Not exercised by CI/tests; worth a pass at some point independent of this.
